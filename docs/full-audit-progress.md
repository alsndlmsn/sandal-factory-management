# تقرير التدقيق والاختبار النهائي

## مصنع الصندل للأوعية البلاستيكية

**الإصدار:** `main` — **التاريخ:** 25 أغسطس 2026 — **إعداد:** Manus AI

## 1. الملخص التنفيذي

اكتملت مراجعة النسخة العربية ذات الاتجاه من اليمين إلى اليسار لنظام مصنع الصندل للأوعية البلاستيكية، المبني باستخدام HTML وCSS وJavaScript وSupabase، والمهيأ للنشر كواجهة ثابتة عبر GitHub Pages. شملت المراجعة القائمة الجانبية، الجداول والأزرار، إدارة المستخدمين، أرشفة الحسابات، الصفحات التشغيلية والمالية، بيانات عرض كبيرة، واختبارات التحمل الوظيفي.

> **حالة التسليم:** النسخة مناسبة للمعاينة والاختبار الداخلي المنظم، وتحتوي بيانات عرض موسومة يمكن للمستخدم رؤيتها وتجربتها. لا ينبغي اعتبارها اعتمادًا محاسبيًا أو شهادة أمان مستقلة أو ضمانًا مطلقًا لعدم الانهيار تحت أي حجم تشغيل قبل معالجة تحذيرات الأمان وإجراء اختبار قبول خاص بالمصنع.

## 3. إدارة المستخدمين والحذف الآمن

أصبح زر الحذف ظاهرًا للمستخدمين غير المديرين فقط. لا يظهر الزر لحساب المدير الحالي، كما تمنع قاعدة البيانات المدير من حذف حسابه. معنى الحذف في هذا النظام هو **حذف المستخدم من التشغيل مع حفظ السجل التاريخي**، وليس حذف السجلات المحاسبية أو حذف الملف المرتبط بالعمليات؛ لأن حذف الملف قد يكسر العلاقات التاريخية بين الموظف والبيع والشراء والقيود.

| الضابط | التنفيذ |
| --- | --- |
| أرشفة الملف | migration `042_user_delete_archive.sql` تضيف `deleted_at` و`deleted_by` إلى `profiles`. |
| RPC محمية | migration `043_admin_user_archive_rpc.sql` تضيف `admin_delete_user(uuid,text)`، وتتحقق من المدير وتمنع حذف الحساب الحالي وتزيل الدور وتسجل السبب. |
| القائمة | صفحة المستخدمين تستعلم `deleted_at` وتستبعد الملفات المؤرشفة من دليل المستخدمين. |
| Auth | وظيفة `admin-delete-user` منشورة بحالة `ACTIVE` مع `verify_jwt=true`. تتحقق من المدير الفعال، تنفذ الأرشفة عند الحاجة، ثم تطبق حظرًا طويل المدة على حساب Auth المستهدف. |
| الجلسة الحالية | عند اكتشاف أن ملف الجلسة غير فعال أو مؤرشف، يخرج التطبيق الجلسة ويعرض رسالة عربية تفيد بأن الحساب موقوف أو مؤرشف. |
| التدقيق | سبب الأرشفة يبقى في سجل النشاط، ولا تُطبع كلمات المرور أو مفاتيح الخدمة أو رموز الجلسات. |

تم اختبار واجهة الإدارة بعد الإصلاح؛ ظهر مستخدمان نشطان فقط في الدليل، واختفى حساب العرض المؤرشف، وبقي حساب المدير بلا زر حذف. جرى نشر وظيفة Auth الآمنة، مع إبقاء الحساب العرضي المؤرشف وعدم محاولة استرجاعه من الواجهة.

## 5. الاختبارات الوظيفية واختبارات الواجهة

شُغّلت الصفحات الرئيسية داخل جلسة المدير، بما في ذلك المنتجات والمخزون والمبيعات والموردون والمشتريات والخزائن والبنوك والتقارير والموظفون والحضور والمرتبات والمستخدمون وسجل التدقيق، ثم شملت الجولة الإنتاج والمرتجعات والتسوية البنكية والقوائم المالية والإعدادات والأدوار. حُمّلت الصفحات دون ظهور شاشة خطأ أو نافذة منبثقة عالقة في اختبار الدخان.

| --- | --- |
| الهاتف بعرض 390 بكسل | حُمّل جدول المنتجات، وأصبح عرض جسم الصفحة 375 بكسل، والحد الأدنى للجدول 0 بكسل، والرأس مخفيًا، والصفوف بطاقات `grid`، وعناوين الخلايا ظاهرة عبر `data-label`، دون تمرير أفقي لجسم الصفحة. |

## 7. فحص قاعدة البيانات والأمان

طُبقت migrations الخاصة بالأرشفة، ونُشرت وظيفة `admin-delete-user` مع اشتراط JWT. لم تُستخدم صلاحيات الخدمة في المتصفح، ولم تُطبع كلمات مرور أو مفاتيح أو رموز جلسات. كما بقيت عمليات الاعتماد والتسوية مرتبطة بمسارات RPC الموجودة في النظام.

| الفحص | النتيجة |
| --- | --- |
| أخطاء مستشار الأمان | 0 |
| تحذيرات مستشار الأمان | 65، من نمط إتاحة دوال `SECURITY DEFINER` للمستخدم المصادق عليه، ويشمل ذلك `admin_delete_user`. |
| أخطاء مستشار الأداء | 0 |
| ملاحظات الأداء المعلوماتية | 97 |
| تحذيرات الأداء | 11، مرتبطة بفهرسة بعض المفاتيح الأجنبية. |
| تجاوز الحماية أثناء إدخال الحضور | لم يتم تجاوز RLS؛ أُنشئت أمثلة الحضور الإدارية بالطريقة الصحيحة بعد رفض إدخال مباشر غير مصرح به. |
| فحص الصياغة | `node --check` نجح لملفات JavaScript وService Worker، و`git diff --check` بلا أخطاء. |
| فحص الأسرار | لم يظهر نمط مفتاح أو رمز خدمة في الملفات المعدلة. |

تحذيرات `SECURITY DEFINER` لا تعني أن العملية مفتوحة بلا تحقق؛ الدوال الحالية تحتوي فحوص صلاحيات داخلية، لكنها تظل ملاحظة أمنية يجب معالجتها في مرحلة لاحقة عبر مراجعة المنح وتقليل الدوال المكشوفة أو نقل غير الضروري منها خارج schema المعروض. مرجع المعالجة العام هو [Supabase Database Linter][1].

## 8. القيود المعروفة قبل التشغيل الحي

الاختبار الحالي **اختبار وظيفي وبياني** وليس اختبار ضغط شاملًا. لم يُقَس الأداء تحت مئات المستخدمين المتزامنين أو انقطاع الشبكة الطويل أو أجهزة ضعيفة أو حجم محاسبي كبير. كما لم يتم تنفيذ تسجيل دخول مستقل بحساب الحسابات داخل المتصفح؛ جرى الاكتفاء بجلسة المدير وفحص الصلاحيات وقواعد البيانات دون طلب أو إعادة طباعة كلمات المرور.

تحذيرات مستشار الأمان ما زالت موجودة، ولذلك لا يصح وصف النظام بأنه خالٍ من المخاطر أو معتمد لمعاملات مالية حية واسعة. يلزم قبل الاعتماد النهائي إجراء مراجعة أمنية لكل RPC، واختبار عملي منفصل لكل دور، ومراجعة محاسبية للسياسات مثل الضرائب، تقييم المخزون، وإقفال الفترات.

زر إعادة ضبط المصنع موجود ضمن الإعدادات للمدير، لكنه إجراء حساس يحذف بيانات التشغيل مع الاحتفاظ بالمستخدمين والصلاحيات. **لم يُستخدم في هذه المرحلة** لأن المستخدم طلب بقاء بيانات العرض، ولا ينبغي الضغط عليه إلا بعد نسخة احتياطية وموافقة واضحة.

## 10. الخلاصة

النسخة الحالية أكثر وضوحًا على الهاتف والكمبيوتر، والقائمة في اليمين، والجداول لا تنضغط على الهاتف بل تتحول إلى بطاقات، وإدارة المستخدمين أصبحت تفرق بين التعليق والأرشفة مع حفظ التاريخ ومنع حذف المدير. كما أن بيانات العرض الكبيرة باقية داخل Supabase وموسومة حتى يستطيع المستخدم تجربة النظام بنفسه.

نتائج مجموعة الاختبار المحددة مطمئنة: 90 عاملًا، و90 بيعًا معتمدًا، و30 شراءً معتمدًا، دون فروقات مالية أو قيود غير متوازنة أو أرصدة مخزون سالبة في الفحص التجميعي. ومع ذلك، فهذه **جاهزية للمعاينة والاختبار الداخلي المنظم** وليست إقرارًا بأن النظام جاهز بلا تحفظ لمعاملات المصنع الحية قبل مراجعة تحذيرات الأمان وإجراء قبول نهائي من المستخدم والمحاسب.

## 11. اختبار الأوفلاين والأونلاين

أضيفت طبقة قراءة محفوظة في المتصفح لآخر نتائج الصفحات التي زارها المستخدم، مع إظهار حالة «وضع أوفلاين». عند عودة الاتصال تُراجع العمليات المؤجلة بطابور واحد يمنع تشغيل مزامنتين في الوقت نفسه، ثم تُرسل نتيجة المزامنة للواجهة لتحديث العدد وإعادة تحميل البيانات.

العمليات الحساسة التي تعتمد على الرصيد أو الاعتماد، مثل البيع والشراء والمرتجع والتحويل والتسوية واعتماد المرتبات، لا تُحفظ مؤجلًا أثناء الانقطاع؛ بل تُرفض برسالة واضحة حتى لا تتكرر العملية أو تُسجل دون تحقق مركزي. الاختبار المباشر قرأ سجلًا محفوظًا أثناء الأوفلاين، ورفض RPC الحساسة، ثم أعاد الاتصال مع طابور متبقٍ يساوي صفرًا. لم تُنفذ عملية بيع أو شراء حقيقية أثناء هذا الاختبار.

> **ملاحظة مهمة:** وضع الأوفلاين هنا وسيلة لاستمرار القراءة الآمنة وعرض البيانات التي سبق تحميلها، وليس بديلًا كاملًا عن Supabase. يجب أن يكون الإنترنت متاحًا عند الحفظ والاعتماد والتسويات المالية. إذا لم تكن صفحة قد زُرِت سابقًا فلا توجد لها نسخة محفوظة أوفلاين، وسيظهر تنبيه بدل عرض بيانات غير مؤكدة.


## 12. إصلاح تسجيل الدخول والأدوار

كان سبب ظهور رسالة «هذا القسم غير متاح لدورك» أن الواجهة كانت تقرأ الملف والدور والصلاحيات من استعلامات منفصلة، ثم تسقط إلى دور `unknown` عند فشل أي استعلام. أضيفت migration `044_current_user_access_rpc.sql` ودالة محمية باسم `get_current_user_access()`، تعيد ملف المستخدم ودوره وأكواد صلاحياته بهوية `auth.uid()` في استجابة واحدة. عند تعذر تحميل الصلاحيات لا تُعرض صفحة فارغة ولا يُمنح دور افتراضي؛ تظهر رسالة عربية تطلب التحقق من الاتصال وإعادة المحاولة.

اختبار قاعدة البيانات أعاد لدور الحسابات الكود `finance` والاسم «حسابات» مع 17 صلاحية، وللمدير الكود `manager` والاسم «مدير». كما اختبرت الواجهة مصفوفة المدير والحسابات والمبيعات والمخزن وموردين والإنتاج؛ ظهرت الأقسام المتوقعة لكل دور ولم يظهر قسم المستخدمين للأدوار غير الإدارية. أضيف زر إظهار وإخفاء كلمة المرور، ونجح تبديله دون إرسال النموذج أو طباعة كلمة المرور. نُشر الإصلاح في commit `c03bfd5`، ونجح سير GitHub Pages رقم `32802506411`.


## 13. تحسين تجربة التنقل والصلاحيات الشخصية

تم تثبيت موضع تمرير القائمة الجانبية في `sessionStorage` واستعادته بعد إعادة بناء الصفحة، بحيث لا يرجع المستخدم إلى أعلى القائمة عند فتح قسم جديد. أضيف لسجل الحضور تمرير رأسي داخلي على سطح المكتب مع رأس جدول ثابت، بينما يتحول السجل وجميع الجداول ذات البيانات إلى بطاقات رأسية على الهاتف، بحيث يظهر عنوان كل حقل فوق قيمته دون ضغط أو تداخل.

تم فصل إعدادات المصنع الإدارية عن تغيير كلمة المرور الشخصية. رابط الإعدادات أصبح يتطلب صلاحية `settings.manage` ولا يظهر لدور الحسابات أو الأدوار التشغيلية، كما أن الحاجز موجود في مسار التنقل والـ RPC الإدارية. في المقابل، يظهر لكل مستخدم زر «كلمة المرور» في الشريط العلوي، ويفتح نافذة مخصصة لتغيير كلمة مرور حسابه الحالي فقط.


## 14. نطاق الصلاحيات والأرباح والخسائر والجاهزية

أضيفت صفحة «صلاحياتي»؛ المستخدم غير المدير يرى أكواد وصلاحيات دوره فقط، بينما المدير يرى المصفوفة الكاملة. وفي الاختبار الصحيح لدور الحسابات كانت صلاحية `settings.manage` غير متاحة، ولم يظهر رابط إعدادات المصنع، مع بقاء تغيير كلمة المرور الشخصية متاحًا. أما المدير فظهرت له إعدادات المصنع ومصفوفة الصلاحيات الكاملة.

احتساب الربح والخسارة موجود بطريقتين مترابطتين. صفحة التقارير التشغيلية تحسب الإيراد من فواتير البيع المعتمدة ناقص تكلفة بنود البيع ثم ناقص المصروفات المعتمدة. والقوائم المالية تحسب قائمة الدخل من القيود المرحّلة، وتعرض التدفقات النقدية والمركز المالي. في لقطة بيانات العرض الحالية: 90 فاتورة بيع معتمدة، إيرادات 2,187 ج.س، تكلفة بضاعة مباعة 1,467 ج.س، هامش إجمالي 720 ج.س، ومصروفات معتمدة 100 ج.س؛ صافي النتيجة المحسوبة لهذه البيانات هو 620 ج.س قبل أي تكاليف غير مسجلة. القيود المرحّلة المفحوصة وعددها 432 قيدًا، ومجموع المدين يساوي مجموع الدائن عند 4,524,354 ج.س.

هذه الأرقام حقيقية حسابيًا من السجلات الموجودة في Supabase، لكنها أرقام عرض واختبار وليست أرباح المصنع الفعلية. لا يصبح الربح الفعلي إلا بعد إدخال كل المبيعات والمشتريات والمصروفات والمرتبات والإهلاك والضرائب والتالف والتسويات والأرصدة الافتتاحية الصحيحة واعتمادها. لذلك تصنيف الجاهزية الحالي هو: جاهز للمعاينة والتجربة الداخلية والبدء التجريبي المنضبط، وليس اعتمادًا نهائيًا لمصنع حقيقي واسع قبل مراجعة محاسب، إدخال البيانات الحقيقية، تجربة تشغيل موازية، وإغلاق الملاحظات الأمنية الموثقة.

## 15. فاتورة المبيعات وهوية المصنع — 2026-08-25

أعيد بناء قالب الطباعة بتنسيق A4 احترافي يتضمن علامة SP، اسم المصنع، رقم المصنع، العنوان، الهاتف والبريد، رقم الفاتورة، العميل، تاريخ الإصدار، طريقة الدفع، جدول بنود حقيقي من `sale_items`، الإجمالي والمدفوع والمتبقي وعبارة أسفل الفاتورة. عند تعذر جلب البنود أو الهوية العامة لا يتوقف فتح نافذة الطباعة؛ يستخدم القالب البيانات المتاحة محليًا ويعرض صفًا احتياطيًا واضحًا بدل إخفاء الفاتورة.

فُصلت حالة «مسدد» عن زر «طباعة» داخل حاوية `sale-actions` مرنة، مع مسافات والتفاف مناسبين للشاشات الصغيرة. أضيفت كذلك أنماط صفحة «صلاحياتي» كي تظهر كبطاقات قابلة للقراءة، مع استمرار قصر الكتالوج الكامل على المدير.

أُضيفت حقول رقم المصنع والعنوان والهاتف والبريد وعبارة أسفل الفاتورة إلى إعدادات المدير، ويجري حفظها عبر التوقيع الموسع لـ `save_factory_settings`. ملف migration 046 موجود محليًا لتوفير `get_factory_identity()` للأدوار غير الإدارية، لكن تطبيقه في Supabase لم يثبت حتى تاريخ هذا التقرير بسبب رفض موصل Supabase برسالة 403 أثناء الاتصال؛ لذلك يجب تطبيقه والتحقق منه قبل اعتبار قراءة هوية المصنع العامة مكتملة على البيئة المنشورة. القيم الفعلية للهاتف والعنوان ورقم المصنع متروكة للمدير ولم تُخترع.

## نظام الإرشاد والتدريب داخل التطبيق — 2026-08-25

أضيف محرك إرشاد عربي RTL مستقل في `js/guidance.js` ومندمج مع التطبيق دون تغيير منطق Supabase أو الصلاحيات. يظهر مركز المساعدة بعد المصادقة فقط، ويظل متاحًا من زر «مساعدة» العلوي والزر العائم واختصار `?`، مع إتاحة دليل الصفحة، طريقة العمل الصحيحة، البحث، الأخطاء الشائعة، الخطوة التالية، شرح الأوفلاين، وتفضيلات مستوى الإرشاد.

تغطي قاعدة الإرشاد الصفحات الحقيقية للنظام: لوحة التحكم، دليل التشغيل، المنتجات، المخزون، الإنتاج، المبيعات، المرتجعات، الموظفون، الحضور، الموردون والمشتريات، الخزائن والبنوك، المصروفات، المرتبات، دفتر اليومية، التقارير، القوائم المالية، التسوية البنكية، سجل التدقيق، المستخدمون، الأدوار، الإعدادات، وصفحة صلاحياتي. الجولات تستخدم عناصر DOM حقيقية وتُسقط الخطوة غير الموجودة بدل اختراع واجهة.

تمت إضافة onboarding قصير قابل للتخطي وإعادة التشغيل، وضع «ما هذا؟» للعناصر المدعومة، حفظ التفضيلات والحالات محليًا لكل مستخدم، زر «كيف أبدأ؟» للحالات الفارغة، وفحص نماذج قبل الإرسال يركز على أول حقل ناقص ويشرح كيفية إصلاحه. أضيف دعم reduced motion وتركيز بطاقة الجولة وحالة الاتصال داخل لوحة المساعدة. اختبار محلي معزول نجح في دليل الصفحة والبحث والتفضيلات والجولة ووضع «ما هذا؟»، كما نجحت إعادة اختبار صفحة الدخول دون ظهور إرشاد قبل المصادقة.

يبقى مركز المساعدة واجهة تعليمية مساعدة ولا يمنح أي صلاحية جديدة. لا ينبغي اعتباره بديلًا عن اختبار قبول عملي لكل دور على جهاز فعلي قبل التشغيل الكامل.

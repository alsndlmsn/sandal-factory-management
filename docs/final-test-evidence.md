# أدلة الاختبار النهائي

بدأ الاختبار النهائي بتاريخ 2026-08-25 بعد التأكد من أن الفرع `main` متزامن مع `origin/main` وأن آخر إصدارين هما `0d55d53` و`0c77ec8`. نجحت فحوص `node --check` لملفات `js/app.js` و`js/supabase.js` و`sw.js`، ونجح `git diff --check` وفحص الأسرار عالي الدقة.

في محاكاة محلية معزولة، تم استدعاء صفحات المنتجات والمبيعات والمخزون والخزائن والمصروفات والموظفين والحضور والمرتبات والموردين والإنتاج والمرتجعات والقيود والقوائم المالية والتسوية البنكية والإعدادات والتقارير والمستخدمين والأدوار وسجل التدقيق وصفحة صلاحياتي. نجحت الصفحات العشرون في إنتاج HTML دون استثناءات.

نجحت assertions الخاصة بمفتاح كلمة المرور، القائمة الإدارية، حقول المنتج، رقم العملية البنكية، إضافة المخزن، بحث الحضور والمرتبات، الأقسام المالية، فلترة التقارير، حقول هوية المصنع وصفحة الصلاحيات. assertion طباعة القيد ظهر غير ناجح في أول المحاكاة لأن قائمة القيود كانت فارغة، لا لأن زر الطباعة غير موجود؛ الكود يحتوي `data-action="journal-print"` وسيتكرر الاختبار بصف قيد فعلي في fixture.


أعيد اختبار صفحة القيود مع قيد تمثيلي غير فارغ (`JE-001`). نجح ظهور رقم القيد، وظهر `data-action="journal-print"` للطباعة، كما ظهر نموذج فلترة القيود. تعثر سكربت fixture كبير سابقًا بسبب خطأ صياغة في سكربت الاختبار نفسه، ثم نجح الاختبار المبسط ولم يظهر خطأ في التطبيق.


في الاختبار الحي الأول لمسار الدفعة اللاحقة، كشف النظام خللًا حقيقيًا في `add_sale_payment`: كانت الدالة تحاول تحديث `remaining_amount` رغم أنه عمود مولّد. أُنشئت migration 047 لتحديث `paid_amount` فقط وترك `remaining_amount` للحساب التلقائي. طُبقت migration 047 بنجاح، ثم أُعيد تشغيل نفس الاختبار بنجاح؛ شمل إنشاء فاتورة غير مسددة واعتمادها وتسجيل الدفعة اللاحقة ثم إنشاء مرتجع واعتماده. لم تُحذف البيانات السابقة، وفشل المحاولة الأولى تراجع بالكامل بسبب تنفيذها داخل معاملة واحدة.

أُثبت قبل ذلك تطبيق migration 046، وأصبح `get_factory_identity()` موجودًا وقابلًا للاستدعاء في قاعدة Supabase الحية. خط الأساس قبل هذه الجولة كان 90 موظفًا و90 فاتورة معتمدة و30 شراءً معتمدًا و132 حركة مخزون و126 قيدًا و616 سجل تدقيق، دون أخطاء اتزان أو مراجع يتيمة.


## نتيجة الجولة الحية النهائية

بعد دورة الاختبار والإصلاح أصبحت المؤشرات الحية: 90 موظفًا، 101 فاتورة بيع معتمدة، 10 فواتير موسومة للاختبار النهائي، وفاتورة واحدة اختُبرت فيها الدفعة اللاحقة حتى أصبح المتبقي صفرًا. اكتمل مرتجع واحد معتمد، ومصروف اختبار واحد معتمد، وشراء اختبار واحد معتمد، وحركة مخزون واحدة معتمدة، وأمر إنتاج واحد معتمد، وفترة مرتب واحدة مجهزة، وسلفة واحدة وحافز واحد. بقيت أخطاء اتزان المبيعات والمشتريات والقيود عند صفر، كما بقيت السجلات اليتيمة لبنود البيع والشراء والمخزون والمدفوعات عند صفر.

كشف الاختبار الأمني أن `anon` كان يملك امتياز التنفيذ العام لثلاث دوال حساسة، فتم تطبيق migration 048 لسحب امتياز `PUBLIC` والإبقاء على `authenticated` فقط. بعد الإصلاح أصبحت امتيازات anon للدوال الثلاث `false` وامتيازات authenticated `true`. ما زالت تظهر تحذيرات Supabase المتعلقة بدوال `SECURITY DEFINER` المتاحة للمستخدمين المسجلين، وهي دوال تعتمد على حواجز صلاحيات داخلية؛ كما توجد ملاحظات أداء عن فهارس مفاتيح أجنبية غير موجودة، ولم تُعتبر هذه الملاحظات شهادة أمان أو أداء مطلق.

اكتشف الاختبار كذلك خللًا وظيفيًا في الدفعة اللاحقة، وأُصلح في migration 047. نجحت إعادة الاختبار بعد التطبيق، ولم تبقَ آثار من محاولة الاختبار الفاشلة لأن المعاملة الأولى تراجعت بالكامل.

# خطة تحويل الأوفلاين إلى IndexedDB ومزامنة آمنة

## الملخص التنفيذي

التحويل إلى IndexedDB مناسب لأن النظام يحتاج إلى تخزين كائنات منظمة وعمليات مؤجلة بطريقة غير متزامنة وقابلة للفهرسة، وهي حالات يتفوق فيها IndexedDB على Web Storage التقليدي [1]. لكن IndexedDB **ليس خزنة سرية بحد ذاته**؛ فأي JavaScript يعمل من نفس أصل الموقع، أو أي شخص يملك وصولًا إلى ملف تعريف المتصفح، قد يقرأ البيانات أو يغيّرها. لذلك يكون التشفير طبقة إضافية، ولا يجوز أن يحل محل التحقق من الصلاحيات على الخادم [3].

في النظام الحالي، توجد ذاكرة قراءة محلية وقائمة عمليات مؤجلة عامة في `js/supabase.js`، بينما العمليات التجارية الحالية تستخدم RPC أو تحديثات مباشرة وتمنع الحفظ عند انقطاع الاتصال في معظم المسارات. لذلك التوصية الآمنة هي تنفيذ المشروع على مرحلتين: نقل ذاكرة القراءة أولًا، ثم بناء طابور للعمليات بعد إضافة Idempotency Keys والتحقق الخادمي. لا ينبغي تفعيل البيع أو المصروفات أو خصم المخزون أو المرتبات أو التسويات أوفلاين قبل اكتمال المرحلة الثانية واختبارها.

> **قاعدة أساسية:** لا تعتبر العملية ناجحة لمجرد حفظها داخل المتصفح. العملية المالية لا تكون ناجحة إلا بعد أن يؤكد Supabase تنفيذها واعتمادها.

## 1. التصميم المقترح للتخزين المحلي

ينبغي إنشاء طبقة مستقلة باسم `offline-store.js` بدل توزيع استدعاءات IndexedDB في كل صفحات التطبيق. هذه الطبقة تكون مسؤولة عن فتح قاعدة البيانات، ترقية مخططها، القراءة والكتابة داخل معاملات IndexedDB، التشفير وفك التشفير، وحدود الحجم والتنظيف.

### مخطط قاعدة IndexedDB

| Object Store | المفتاح | المحتوى | السياسة |
|---|---|---|---|
| `read_cache` | `cache_key` | نتائج قراءة محدودة مع وقت آخر مزامنة ومدة صلاحية | لا تُخزن كلمات المرور أو رموز الجلسة. تُعرض دائمًا مع وقت آخر تحديث |
| `outbox` | `idempotency_key` | عملية مؤجلة، اسم العملية، حمولة مشفرة، الحالة، المحاولات، آخر خطأ | لا تُنشأ إلا للعمليات التي يدعم خادمها Idempotency |
| `sync_receipts` | `idempotency_key` | نتيجة المزامنة ومرجع السجل الخادمي | تساعد على عدم إعادة عرض العملية أو إعادة إرسالها |
| `metadata` | اسم ثابت | إصدار المخطط، آخر مزامنة، حالة قفل الجهاز | لا تُخزن فيه أسرار أو مفاتيح قابلة للاستخراج |

يجب أن تحتوي كل قيمة في `read_cache` و`outbox` على `schema_version` و`created_at_client` و`updated_at_client`. وقت الجهاز ليس مصدرًا محاسبيًا؛ عند اعتماد العملية يجب أن يأتي وقتها النهائي من الخادم، مع الاحتفاظ بوقت الجهاز للمقارنة والتدقيق فقط.

### خطوات التحويل من localStorage

يتم أولًا إضافة قاعدة IndexedDB جديدة بإصدار مستقل، ثم نقل ذاكرة القراءة القديمة مرة واحدة إلى `read_cache` إذا كانت قابلة للقراءة. بعد نجاح النقل، تُحذف مفاتيح الكاش القديمة فقط، ولا تُحذف بيانات المستخدم أو بيانات Supabase. ينبغي الاحتفاظ بعلامة `migration_completed_v1` حتى لا تتكرر عملية النقل.

بعد ذلك تُستبدل الدوال المتزامنة الحالية مثل `readCache` و`writeCache` بدوال غير متزامنة مثل `idbCacheGet` و`idbCachePut`. هذه النقطة مهمة لأن IndexedDB غير متزامن؛ لا ينبغي وضع غلاف شكلي يعيد دوال متزامنة أو يوقف واجهة المستخدم.

يجب تحديد حد أقصى للكاش، مثل عدد سجلات أو حجم تقريبي، وحذف الأقدم عند تجاوز الحد. عند امتلاء مساحة المتصفح أو تلف قاعدة البيانات، يجب إظهار رسالة واضحة للمستخدم بدل التعامل مع الخطأ على أنه قائمة فارغة.

## 2. أفضل ممارسة للتشفير المحلي

يوفر Web Crypto API عمليات تشفير منخفضة المستوى، وهو متاح في السياقات الآمنة مثل HTTPS، لكنه سهل الاستخدام بصورة خاطئة؛ لذلك لا ينبغي اختراع خوارزمية أو وعد المستخدم بحماية مطلقة [2]. التكوين العملي المقترح هو **AES-GCM بمفتاح 256 بت**، مع IV عشوائي جديد لكل سجل، وبيانات مرتبطة AAD تمنع نقل ciphertext إلى سجل آخر.

### إدارة المفتاح

الخيار الأكثر وضوحًا لبيانات المصنع هو أن يفتح المستخدم الجهاز بكلمة مرور أو PIN محلي لا يتم حفظه. تُشتق من كلمة المرور مفتاح حماية باستخدام PBKDF2-HMAC-SHA-256 مع `salt` عشوائي محفوظ مع البيانات. عدد دورات PBKDF2 لا يُنسخ بصورة عمياء؛ يتم اختياره بعد قياس زمن الفتح على أقل جهاز مستهدف، ويُحفظ مع إصدار المخطط حتى يمكن ترقيته مستقبلًا.

بعد اشتقاق مفتاح التشفير، لا يُحفظ نص كلمة المرور ولا مفتاح مشتق قابل للتصدير في `localStorage`. يمكن الاحتفاظ بكائن `CryptoKey` غير قابل للتصدير داخل IndexedDB لجلسة الجهاز، لكن ذلك يحمي التخزين الساكن أكثر مما يحمي الصفحة أثناء فتحها؛ فإذا أُصيب الموقع بـ XSS يستطيع الكود الخبيث استخدام المفاتيح المتاحة في الجلسة. توضح OWASP أن تشفير بيانات المتصفح لا يحمي من كل تهديدات الجهاز أو XSS، وأن بيانات IndexedDB يجب معاملتها كمدخلات غير موثوقة عند قراءتها [3].

لا ينبغي حفظ مفتاح التشفير بجانب البيانات المشفرة في نفس المتجر بطريقة قابلة للقراءة. ذلك يعطي إحساسًا زائفًا بالأمان. كما لا ينبغي تخزين رموز جلسة Supabase أو كلمات المرور في IndexedDB؛ توصي OWASP بعدم وضع رموز الجلسات والأسرار في تخزين العميل [3].

### شكل تشفير السجل

كل سجل مشفر يمكن أن يكون على الشكل التالي:

```js
{
  version: 1,
  algorithm: "AES-GCM",
  key_version: 1,
  iv_b64: "...",
  salt_id: "device-salt-1",
  aad: "outbox|<idempotency-key>|v1",
  ciphertext_b64: "...",
  created_at_client: "..."
}
```

التطبيق العملي يستخدم `crypto.subtle.encrypt` و`crypto.subtle.decrypt`، ويفشل مغلقًا عند عدم القدرة على فك التشفير. لا يُسمح بعرض حمولة غير مفكوكة على أنها عملية صحيحة، ولا يتم تجاوز فشل التحقق من GCM.

### ما الذي نشفره؟

| البيانات | التوصية |
|---|---|
| كلمات المرور ورموز الجلسة | لا تُحفظ في مخزن التطبيق أصلًا |
| بيانات العملاء والموظفين | أقل قدر ممكن، ومشفرة إذا كانت ستبقى أوفلاين |
| بيانات الرواتب والسلف | لا تُخزن أوفلاين إلا مع قفل محلي ومبرر تشغيلي واضح |
| نتائج قراءة عامة مثل أسماء المنتجات | يمكن تخزينها مع تصنيف حساسية، والتشفير مفضل إذا كان الجهاز مشتركًا |
| مفاتيح Idempotency | يمكن تخزينها لأنها معرفات وليست أسرارًا، لكن تُعامل كبيانات داخلية ولا تتضمن بريدًا أو رقم هوية |
| صلاحيات المستخدم | لا تُستخدم كمرجع ثقة؛ الكاش يساعد العرض فقط، والخادم يعيد التحقق |

## 3. Idempotency Key والمزامنة الآمنة

مفتاح Idempotency هو معرف فريد تنشئه الواجهة مرة واحدة للعملية، ثم تعيد استخدامه في كل المحاولات. إذا انقطع الاتصال بعد تنفيذ الخادم وقبل وصول الاستجابة، فإن إعادة نفس المفتاح تسمح للخادم بإرجاع النتيجة السابقة بدل إنشاء فاتورة أو مصروف أو حركة مخزون ثانية. توصي وثائق Stripe باستخدام UUID عشوائي وعدم تضمين بيانات حساسة في المفتاح، ومقارنة معاملات الطلب عند إعادة استخدامه [4].

### دورة العملية

1. عند إنشاء مسودة محلية، ينشئ التطبيق `crypto.randomUUID()` ويحفظه في سجل `outbox`.
2. يتم تثبيت المفتاح وعدم تغييره عند الضغط المتكرر أو إعادة فتح الصفحة أو إعادة المحاولة.
3. تُحسب بصمة معيارية للحمولة بعد ترتيب الحقول وإزالة الحقول غير الدلالية.
4. يرسل العميل اسم العملية، المفتاح، بصمة الحمولة، والحمولة إلى RPC خادمية محمية.
5. يسجل الخادم مفتاح العملية وبصمتها قبل تنفيذ الأثر التجاري، داخل نفس المعاملة.
6. إذا وجد المفتاح من قبل، يقارن الخادم البصمة؛ فإذا تطابقت يُرجع النتيجة السابقة، وإذا اختلفت يرفض الطلب باعتباره إعادة استخدام خطرة.
7. بعد نجاح المعاملة، يضع العميل العملية `succeeded` ويحفظ رقم السجل الخادمي.
8. إذا كان الخطأ صلاحية أو تحققًا أو رصيدًا غير كافٍ، توضع العملية `failed_permanent` وتحتاج تدخلًا، ولا تعاد تلقائيًا.

### ما يجب إضافته في Supabase

ينبغي إنشاء جدول إيصالات عمليات، مثل `operation_receipts`، يحتوي على `factory_id` أو نطاق المصنع، و`idempotency_key`، و`operation_name`، و`request_hash`، و`user_id`، و`status`، و`response_payload`، و`created_at` و`completed_at`. يُنشأ قيد Unique على نطاق المصنع والمفتاح.

كل RPC حساسة، مثل اعتماد البيع أو المصروف أو حركة المخزون، يجب أن تستقبل المفتاح والبصمة، وتنفذ الآتي داخل معاملة واحدة:

| المرحلة | تحقق الخادم |
|---|---|
| المصادقة | `auth.uid()` صالح والجلسة غير منتهية |
| الصلاحية | المستخدم يملك صلاحية العملية وقت المزامنة، لا وقت إنشاء المسودة فقط |
| النطاق | العملية تخص المصنع المسموح للمستخدم ولا تقبل `factory_id` من العميل دون تحقق |
| التكرار | المفتاح غير موجود، أو موجود بنفس البصمة والنتيجة محفوظة |
| سلامة البيانات | الكمية والسعر والرصيد والمرجع مرتبطة بسجلات حقيقية |
| الأثر التجاري | الإيصال والقيود وتغيير المخزون والعملية نفسها تنفذ معًا |
| التدقيق | يسجل المستخدم ووقت الخادم والعملية والحالة قبل/بعد عند الحاجة |

Idempotency Key لا يثبت هوية المستخدم ولا يمنح صلاحية. هو فقط يمنع تكرار نفس الطلب. لا يجوز أن تعتمد RLS أو RPC على قيمة الدور المخزنة في المتصفح، ولا أن تعتبر نجاح إدخال `operation_receipts` وحده نجاحًا للبيع أو الصرف.

### حالات طابور المزامنة

```text
pending
  -> sending
  -> succeeded
  -> failed_retryable
  -> failed_permanent
  -> conflict
```

تستخدم `failed_retryable` إعادة محاولة بتدرج زمني، مثل 2 ثم 4 ثم 8 دقائق مع حد أقصى، ولا تستخدم إعادة المحاولة اللانهائية. تُرتب العمليات حسب اعتمادها؛ فلا تُرسل عملية بيع تعتمد على منتج أو مخزن لم تتم مزامنته. وفي حالة أكثر من تبويب، يجب استخدام قفل مشترك أو `BroadcastChannel` حتى لا يرسل تبويبان نفس العملية معًا. يظل القفل الخادمي بالمفتاح الفريد هو الحماية النهائية.

## 4. خطة التنفيذ المرحلية

| المرحلة | التنفيذ | معيار الخروج |
|---|---|---|
| 0 | إبقاء العمليات المالية أوفلاين معطلة، وإضافة طبقة IndexedDB لذاكرة القراءة فقط | القراءة تعمل، ووقت آخر مزامنة واضح، ولا تتأثر الجلسة |
| 1 | إضافة قفل محلي وتشفير للكاش الحساس، مع تنظيف localStorage القديم الآمن | لا توجد رموز جلسة أو كلمات مرور في المخازن الجديدة، وفشل فك التشفير مغلق |
| 2 | إضافة جدول إيصالات ومفاتيح Idempotency إلى RPC واحدة غير مالية أو مسودة | تكرار الطلب بنفس المفتاح يعيد نفس النتيجة ولا ينشئ سجلًا ثانيًا |
| 3 | تفعيل طابور للمسودات غير الحساسة فقط | الإغلاق وإعادة الفتح والانقطاع لا يفقدان المسودة، وكل حالة ظاهرة |
| 4 | اختبار بيع أو مصروف أو حركة مخزون أوفلاين في بيئة اختبار منفصلة، لا في بيانات المصنع الحية | اجتياز اختبارات التكرار والتعارض والصلاحيات والتدقيق |
| 5 | قرار تشغيل محدود لكل عملية بعد قبول المدير والعميل | وجود مفتاح إيقاف عام يعيد النظام إلى Online-only عند أي خلل |

يوصى بإضافة متغير تشغيل مثل `OFFLINE_MUTATIONS_ENABLED=false` في البداية. لا يكفي إخفاء زر أوفلاين؛ يجب أن يرفض الخادم أي مسار غير مدعوم، وأن يظهر التطبيق سبب الرفض بوضوح.

## 5. خطة الاختبار الشاملة

### أدوات الاختبار

يتم استخدام Chrome DevTools لتفعيل Offline وSlow 3G، وإيقاف الشبكة من أكثر من نقطة، وإعادة تحميل الصفحة، وإغلاق التبويب، ومسح بيانات الموقع. وللاختبارات المتكررة يُفضّل استخدام Playwright أو أداة متصفح آلية مع قاعدة Supabase اختبارية، مع عدم تشغيل سيناريوهات الحذف أو إعادة ضبط المصنع على بيانات العرض الحية.

### مصفوفة السيناريوهات

| ID | السيناريو | الإجراء | النتيجة المتوقعة |
|---|---|---|---|
| OFF-01 | تشغيل طبيعي | افتح النظام متصلًا وسجل وقت المزامنة | تظهر البيانات الحديثة ولا يوجد طابور معلق |
| OFF-02 | انقطاع قبل القراءة | افصل الشبكة ثم افتح صفحة لم تُحفظ | رسالة واضحة بعدم توفر نسخة محلية، دون بيانات وهمية |
| OFF-03 | انقطاع بعد القراءة | افتح صفحة، افصل الشبكة، أعد فتحها | تظهر آخر نسخة مع تاريخ ووقت آخر مزامنة ووسم «قديمة» |
| OFF-04 | إعادة تحميل أوفلاين | افصل الشبكة وأعد تحميل النظام | لا تنهار الواجهة، ويظهر الوضع أوفلاين بوضوح |
| OFF-05 | عودة الاتصال | أعد الشبكة من دون إعادة تحميل | ينجح فحص الاتصال وتبدأ المزامنة مرة واحدة |
| OFF-06 | انقطاع أثناء طلب GET | ابدأ القراءة ثم اقطع الشبكة | لا تُستبدل نسخة سليمة بكاش ناقص أو فارغ |
| OFF-07 | انقطاع قبل POST | اقطع الشبكة قبل إرسال عملية حساسة | العملية تُرفض حاليًا أو تتحول لمسودة معلنة، ولا يظهر نجاح كاذب |
| OFF-08 | انقطاع بعد تنفيذ الخادم | اسمح بوصول الطلب ثم اقطع الاستجابة | إعادة نفس المفتاح تعيد النتيجة السابقة ولا تنشئ سجلًا ثانيًا |
| OFF-09 | ضغط مزدوج | اضغط اعتماد الفاتورة مرتين بسرعة | سجل تجاري واحد فقط، أو منع الضغط الثاني بصريًا وخادميًا |
| OFF-10 | إعادة تحميل أثناء الإرسال | أرسل عملية ثم أغلق التبويب فورًا | تبقى في `outbox` بحالتها الصحيحة ولا تفقد المفتاح |
| OFF-11 | إعادة المحاولة | أعد إرسال عملية `failed_retryable` عدة مرات | لا تكرار، وتزداد المحاولات بتدرج، وتتوقف عند الحد |
| OFF-12 | تغيير الحمولة | أعد استخدام المفتاح نفسه مع مبلغ مختلف | رفض `conflict` وعدم تعديل النتيجة الأولى |
| OFF-13 | صلاحية تغيرت | أنشئ مسودة، اسحب الصلاحية، ثم أعد الاتصال | يرفض الخادم العملية وتسجل كفشل دائم، ولا يتجاوز المستخدم الصلاحية |
| OFF-14 | انتهاء الجلسة | اقطع الشبكة حتى تنتهي الجلسة ثم أعدها | لا تُرسل العملية قبل تجديد الجلسة أو تسجيل الدخول، ولا تستخدم كاش الصلاحيات كسلطة |
| OFF-15 | جهازان أو تبويبان | أنشئ عمليتين متعارضتين على جهازين | يمنع الخادم التكرار أو يكشف التعارض، ولا يدمج المخزون بصمت |
| OFF-16 | ترتيب الاعتماد | أنشئ عملية تعتمد على منتج أو مخزن غير متزامن | تحفظ بالترتيب أو تبقى معلقة بسبب الاعتماد، ولا تفشل بصورة غامضة |
| OFF-17 | ساعة الجهاز | غيّر ساعة الجهاز قبل إنشاء مسودة | وقت الاعتماد النهائي من الخادم، والفرق ظاهر للتدقيق إن لزم |
| OFF-18 | مسح التخزين | امسح Site Data قبل عودة الاتصال | يظهر فقدان الكاش/المسودات بوضوح، ولا يدعي النظام أنها محفوظة |
| OFF-19 | مساحة ممتلئة | امنع التخزين أو املأه حتى يفشل الحفظ | رسالة فشل واضحة، وعدم اعتبار العملية محفوظة |
| OFF-20 | تلف البيانات | عدّل سجلًا مشفرًا أو احذف جزءًا من ciphertext | يفشل فك التشفير مغلقًا ويطلب إعادة المزامنة أو تسجيل الدخول |
| OFF-21 | قفل الجهاز | اترك النظام دون نشاط ثم حاول فتح العمليات | يطلب فتح القفل المحلي ولا يعرض بيانات حساسة قبل ذلك |
| OFF-22 | XSS/فحص التخزين | افحص localStorage وIndexedDB وApplication tab | لا توجد كلمات مرور أو رموز جلسة أو بيانات غير لازمة مكشوفة |
| OFF-23 | Service Worker قديم | افتح نسخة قديمة ثم انشر تحديثًا | يتحدث الكاش، ولا يقدم العامل نسخة قديمة بصورة صامتة بعد التحديث |
| OFF-24 | فشل RPC | أعد خطأ 401 أو 403 أو RLS أو 409 أو 500 | تصنف العملية حسب النوع، ولا تعاد أخطاء الصلاحية تلقائيًا |
| OFF-25 | مزامنة كبيرة | حمّل طابورًا من 90 عاملًا وعددًا كبيرًا من الفواتير التجريبية | لا تجمد الواجهة، ويظهر التقدم، ولا تتكرر السجلات |
| OFF-26 | استعادة بعد فشل جزئي | اجعل بعض العمليات تنجح وبعضها تفشل | يعرض النظام نتيجة كل عملية، ولا يخفي العمليات الباقية |
| OFF-27 | تسجيل التدقيق | نفذ إنشاء/إرسال/رفض/نجاح/تعارض | يسجل وقت الخادم والمستخدم والمفتاح والنتيجة دون حفظ أسرار |
| OFF-28 | العودة المتكررة | شغّل وأوقف الشبكة عدة مرات | لا تتكرر المستمعات ولا تبدأ مزامنة متوازية لنفس الطابور |

### اختبارات القبول

لا يُقبل تفعيل أي كتابة أوفلاين حساسة إلا إذا تحققت الشروط الآتية: لا توجد عملية تجارية مكررة بعد عشر محاولات إعادة لنفس المفتاح، لا يمكن لمستخدم غير مصرح له اعتماد عملية، لا تضيع عملية دون أن تظهر في حالة معلقة أو فاشلة، لا تُعرض نسخة قديمة دون وسم وقتها، وتبقى القيود وسجل التدقيق متسقة بعد نجاح المزامنة.

كما يجب أن يثبت الاختبار أن تبديل الشبكة أثناء كل مرحلة لا يترك النظام في حالة نجاح كاذب. ويجب أخذ نسخة من نتائج الاختبارات، وسجل RPC، وعدد السجلات قبل وبعد، ومفاتيح العمليات المستخدمة للاختبار دون تضمين بيانات حساسة في التقرير.

## 6. ضوابط التشغيل في المصنع

في التشغيل الأول، تكون المبيعات والمصروفات والمخزون والمرتبات والتسويات **Online-only**. يسمح الأوفلاين بالقراءة المحدودة والمسودات غير الحساسة فقط. يظهر في أعلى الواجهة اتصال/أوفلاين، ووقت آخر مزامنة، وعدد العمليات المعلقة، مع زر «مراجعة المزامنة» للمدير.

يجب تخصيص جهاز لكل مستخدم أو حساب Windows منفصل، وتفعيل قفل الشاشة، ومنع مشاركة حسابات الموظفين، وتسجيل الخروج عند نهاية الوردية. التشفير المحلي لا يعوض حماية الجهاز أو معالجة XSS؛ تخزين العميل لا يوفر سرية مطلقة [3].

يجب الاحتفاظ بنسخة احتياطية خادمية دورية، ومراجعة العمليات المرفوضة أو المتعارضة يوميًا في فترة التشغيل التجريبي. ويجب وجود مفتاح إيقاف يعيد جميع العمليات إلى الاتصال المباشر إذا ظهرت مشكلة في التكرار أو التعارض.

## القرار الموصى به لنظام مصنع الصندل

التنفيذ الآمن ليس «نقل localStorage إلى IndexedDB ثم فتح البيع أوفلاين». القرار الصحيح هو: IndexedDB للكاش والمسودات، Web Crypto لحماية البيانات الساكنة، Idempotency على مستوى RPC وقاعدة البيانات، ثم اختبار الانقطاع في بيئة منفصلة قبل السماح بأي أثر مالي. بهذه الطريقة يستفيد المصنع من استمرار القراءة والتحضير دون أن تتحول الشبكة الضعيفة إلى فواتير مكررة أو أرصدة خاطئة.

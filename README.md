# نظام إدارة مصنع الصنادل البلاستيكية

تطبيق ويب عربي RTL لإدارة مصنع الصنادل البلاستيكية. الواجهة مبنية باستخدام **HTML5 وCSS3 وJavaScript ES Modules فقط**، وتعمل كموقع ثابت على GitHub Pages. يستخدم التطبيق Supabase للمصادقة وقاعدة PostgreSQL وسياسات Row Level Security ودوال RPC الحرجة.

> هذا المشروع لا يعرض بيانات تجريبية. قبل تسجيل الدخول سيظهر إعداد النظام، وبعد الاتصال يعرض التطبيق بيانات Supabase المصرح بها فقط.

## بنية المشروع

```text
.
├── index.html
├── 404.html
├── .nojekyll
├── assets/
│   ├── config.example.js
│   ├── supabase-client.js
│   ├── auth.js
│   ├── router.js
│   ├── api.js
│   ├── app.js
│   └── styles.css
├── supabase/
│   ├── schema.sql
│   └── functions/
│       └── admin-user-management/index.ts
├── TESTING.md
└── README.md
```

## التشغيل المحلي

لا يحتاج الموقع إلى Node.js أو خادم تطبيق. انسخ الإعداد النموذجي:

```bash
cp assets/config.example.js assets/config.js
```

ثم افتح `assets/config.js` وضع **رابط مشروع Supabase والمفتاح العام publishable/anon فقط**. لا تضع `service_role` أو كلمة مرور قاعدة البيانات أو أي مفتاح سري. لأن المتصفح يحتاج ملف الإعداد، يبقى `config.js` محليًا ولا يرفع إلى مستودع عام.

للتجربة المحلية، استخدم خادم ملفات ثابتًا بسيطًا من أي بيئة تطوير، مثل خادم Live Server في محرر الأكواد. لا تستخدم `file://` لأن وحدات ES وطلبات Supabase تحتاج أصل HTTP.

## إعداد Supabase

افتح Supabase Dashboard ثم SQL Editor، والصق الملف `supabase/schema.sql` ونفذه مرة واحدة. ينشئ الملف الجداول والأنواع والقيود والفهارس وسياسات RLS ودوال RPC والمشاهد المستخدمة للرصيد والتنبيهات والمطابقة.

بعد ذلك أنشئ المستخدمين الخمسة من **Authentication → Users** أو من مسار إداري آمن. لا ينشئ المتصفح مستخدمين إداريين ولا يستخدم مفتاحًا مميزًا. سيُنشئ trigger ملف `profiles` بعد إنشاء مستخدم Auth. يحدد مدير النظام الدور من خلال مسار إداري آمن، أو يعدل الدور الأول مرة واحدة من SQL Editor بعد التحقق من هوية المستخدم:

```sql
update public.profiles
set role = 'manager', full_name = 'اسم مدير النظام'
where email = 'manager@example.com';
```

الأدوار المسموح بها هي `manager` و`sales` و`warehouse` و`cashier` و`payroll` فقط. كل مستخدم يبدأ بصلاحية المبيعات ما لم يحدد مدير النظام خلاف ذلك. لا تعتمد الواجهة على إخفاء الأزرار للحماية؛ الحماية الفعلية داخل RLS ودوال RPC.

## إعداد الدخول وGitHub Pages

في Supabase من Authentication → URL Configuration ضع القيمة الدقيقة التالية بعد معرفة اسم حساب GitHub واسم المستودع:

```text
Site URL:
https://GITHUB_USERNAME.github.io/REPOSITORY_NAME/

Additional Redirect URLs:
https://GITHUB_USERNAME.github.io/REPOSITORY_NAME/
```

في هذا المشروع يكون اسم المستودع `sandal-factory-management`. ارفع الملفات إلى فرع `main`، ثم من إعدادات المستودع افتح Pages واختر **Deploy from a branch**، وحدد `main` ومجلد `/ (root)`. وجود `.nojekyll` و`404.html` والتنقل عبر hash يجعل التحديث داخل مسار GitHub Pages آمنًا.

GitHub Pages ينشر ملفات ثابتة عامة؛ لذلك لا تخزن فيه أي بيانات تشغيلية أو مفاتيح سرية. بيانات المصنع تبقى في Supabase وتُحمى بالمصادقة وRLS.

## Edge Function لإدارة المستخدمين

إعادة تعيين كلمة المرور وتعطيل الحسابات وتغيير الأدوار لا تنفذ من JavaScript في المتصفح. المصدر موجود في:

```text
supabase/functions/admin-user-management/index.ts
```

انشر الدالة من بيئة Supabase الآمنة، وضع `SUPABASE_SERVICE_ROLE_KEY` كـ **Secret داخل Edge Functions فقط**. لا تنسخ المفتاح إلى GitHub أو `config.js` أو سجلات التشغيل. الدالة تتحقق من JWT ومن دور المدير وتطلب سببًا وتطبق تحديدًا لمحاولات الإدارة. لا تعيد كلمة المرور المؤقتة إلى المتصفح ولا تخزنها في سجل التدقيق.

إجراءات إدارة المستخدم التي يدعمها التصميم هي تعيين كلمة مرور مؤقتة، إرسال رسالة استرداد، تعطيل المستخدم، تفعيله، وتغيير دوره. كلمة المرور المؤقتة لا تقل عن 12 حرفًا، وبعد الدخول تظهر شاشة تغيير كلمة المرور ويظل الوصول إلى بيانات المصنع مقفولًا حتى إكمال التغيير.

## الضوابط المحاسبية والأمنية

المستندات المعتمدة لا تُعدّل أو تُحذف من الواجهة. عمليات اعتماد المبيعات والمخزون والحسابات والمصروفات والرواتب تمر عبر دوال PostgreSQL محددة، مع فحص الدور والجلسة والقيود والرصيد والتكرار. تُشتق أرصدة المخزون والنقدية والبنوك من السجلات المعتمدة، ولا يوجد حقل رصيد حالي قابل للتعديل.

العملة الوحيدة هي الجنيه السوداني `ج.س / SDG`. تخزن القيم المالية في PostgreSQL كـ `numeric(18,2)`، وتستخدم الدوال الحسابية داخل PostgreSQL. تعرض الواجهة القيم بواسطة `formatSDG` الموحد، وتخزن التواريخ كـ UTC `timestamptz` وتعرضها بتوقيت `Africa/Khartoum`.

المبيعات في النسخة الأولى نقدية أو بنكية فقط. البيع البنكي يتطلب مرجعًا فريدًا، ولا توجد مبيعات آجلة أو ذمم مدينة. اعتماد البيع ينشئ حركة مخزون وحركة تحصيل مرتبطة به، وتستخدم بنود البيع لقطة السعر وقت الإنشاء حتى لا تغير الأسعار اللاحقة التاريخ.

## الطباعة والتقارير

التقارير تستخدم البيانات المصرح بها فقط وتوفر حالات التحميل والفراغ والخطأ. توجد CSS للطباعة على A4 للتقارير والفواتير، وA5 للقسائم، وأحجام حرارية تقريبية 80mm و58mm. استخدم زر طباعة الصفحة من وحدة التقارير، ويمكن تصدير الصفوف المسموح بها إلى CSV من داخل المتصفح.

## قائمة النشر

| الخطوة | الحالة المطلوبة |
|---|---|
| نسخ `config.example.js` إلى `config.js` وإدخال المفتاح العام فقط | قبل التشغيل |
| تنفيذ `supabase/schema.sql` في SQL Editor | قبل إنشاء البيانات |
| إنشاء مستخدمين Auth الخمسة | قبل اختبار الأدوار |
| إنشاء ملفات profiles وتعيين الأدوار | قبل تسجيل الدخول |
| نشر Edge Function ووضع السر داخل Supabase فقط | قبل إدارة المستخدمين |
| ضبط Site URL وRedirect URL | قبل اختبار OAuth/session |
| تفعيل GitHub Pages من `main` و`root` | قبل الإنتاج |
| اختبار كل دور والرصيد السالب والتكرار والطباعة والجوال | قبل التسليم |

## ملاحظات مهمة

التطبيق يحتاج اتصال إنترنت حتى يتصل بـ Supabase، ويعرض خطأ عربيًا عند انقطاع الشبكة أو انتهاء الجلسة. لا تستخدم أرقامًا أو أسماءً وهمية لإخفاء فشل الإعداد. إذا لم يتم إدخال رابط Supabase والمفتاح العام سيظهر تنبيه الإعداد بدل لوحة تحكم فارغة أو مزيفة.
